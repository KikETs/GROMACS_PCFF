The update-thread override did not materially improve OMP16. `GMX_PCFF_EXACT_RESPA_UPDATE_OMP_THREADS=4` and `=8` runs were started as diagnostics but hung after startup and were killed; they are excluded from valid performance comparisons.

The effective fix for the OMP16 cliff is to cap exact r-RESPA GPU runs to 8 OpenMP threads by default, even when `-ntomp 16` is requested. The patched runner logs:

`Limiting OpenMP threads for exact r-RESPA GPU nonbonded to 8 (previous requested value: 16).`

This restored pme4 `-ntomp 16` from 64.870 ns/day to 182.488 ns/day on the 20000-step probe. The opt-out env `GMX_PCFF_EXACT_RESPA_GPU_CAP_EXPLICIT_NTOMP=0` preserves explicit 16-thread behavior and reproduces the slow path.

## 2026-07-03 cleanup notes

The `batched native add-F` host-reduction patch was removed after analysis. It tried to share one OpenMP atom-range split across multiple native multi force-output targets, but the 4000-step pme4 retest slowed to 168.582 ns/day. The timing table showed the intended target moved the wrong way: `NB X/F buffer ops.` increased to 0.079 s versus the 0.058 s class2 reference, and `eR bond add F` increased to 0.052 s versus 0.032 s. The likely cause is poorer cache locality from looping over multiple target force arrays inside each atom chunk. The build after removing this patch completed successfully.

The cleaned path was remeasured after the GPU became idle. The pme4 20000-step baseline recovered to `188.037 ns/day` (`0.230 ms/step`), slightly above the previous class2 baseline (`186.706 ns/day`). The useful timing deltas were in the intended host-side regions: `NB X/F buffer ops.` improved from `0.339 s` to `0.312 s`, `eR GPU add F` from `0.103 s` to `0.089 s`, and `eR bond add F` from `0.181 s` to `0.175 s`.

Additional pme4 20000-step negative controls:

- Disabling bonded/CPU-listed overlap slowed the run to `186.467 ns/day`, so the overlap path should stay enabled.
- Disabling deferred native-multi nonbonded wait slowed the run to `185.322 ns/day`, so the deferred wait path should stay enabled.
- Forcing the requested `-ntomp 16` by disabling the exact GPU ntomp cap slowed the run to `148.793 ns/day`. The bad regions were `NB X/F buffer ops.` (`0.312 -> 0.584 s`), `Update` (`0.127 -> 0.414 s`), `eR GPU add F` (`0.089 -> 0.156 s`), and `eR bond add F` (`0.175 -> 0.269 s`). The 8-thread cap is therefore intentional for this 7.9k-atom exact r-RESPA GPU case.
- Disabling the exact GPU bonded list cache slowed the run to `125.960 ns/day`; `eR bond list` jumped from `0.038 s` to `1.820 s`. The list cache is required, not optional polish.

The small-system NBNXM force-reduction auto-serial experiment was removed. It looked neutral-to-slightly-positive in one capped 8-thread probe, but the later OMP16 investigation showed the worker-selection/env-query changes were unsafe for the hot path: forced OMP16 dropped to about `66 ns/day` and the slowdown appeared broadly in `NB X/F buffer ops.`, `eR GPU add F`, `eR bond add F`, `Update`, and `eR CPU listed`. The final tree keeps the original NBNXM reduction loop.

The OMP16-safe optimization remains the runner-level exact r-RESPA GPU cap to 8 threads. Attempts to keep actual 16 threads and reduce only selected module/force-add workers either slowed heavily or stalled after startup. Actual-16 is not abandoned: `GOMP_SPINCOUNT=7000 OMP_WAIT_POLICY=active` recovered the current actual-16 path from `66.228` to `104.063 ns/day`, showing that OpenMP wake/sleep/barrier behavior is a real part of the cliff. In-process `setenv` from `runner.cpp` was tested and removed because libgomp had already consumed the wait-policy state by that point.

Further OMP16 follow-up:

- `GMX_PCFF_EXACT_RESPA_GPU_BONDED_FTYPES=class2-pair14` removed `eR CPU listed`, but 20000-step performance fell to `100.849 ns/day` because `NB X/F buffer ops.` and GPU bonded add/wait increased. The default remains narrow `class2`.
- Forcing exact r-RESPA update thread counts is not accepted. `UPDATE_OMP_THREADS=1` reduced the update timer but slowed total 4000-step throughput (`98.189 -> 94.096 ns/day`), while `UPDATE_OMP_THREADS=2` stalled after startup and was killed.

- Reusing exact r-RESPA force-output storage is now enabled by default and can be disabled with `GMX_PCFF_EXACT_RESPA_REUSE_FORCE_OUTPUT_STORAGE=0`. The accepted version uses thread-local unpinned storage. The first pinned thread-local attempt reduced 4000-step force setup time but failed at shutdown with `cudaFreeHost failed`; unpinned reuse removed that error and improved actual-16 20000-step throughput from a three-run off average of `103.459 ns/day` to an on average of `107.392 ns/day`. Final default-vs-optout checks gave actual-16 `105.339` vs `102.346 ns/day` and capped path `192.754` vs `187.354 ns/day`.
- A 100-step A/B check for force-output storage reuse produced identical `.edr` and `.trr` hashes. The final `.gro` hash differed only at the usual last printed coordinate/velocity digits seen in baseline GPU run-to-run comparisons (`max_pos_nm=0.001`, `max_vel=0.001288`).
- A `usingLJPme` setup bug in `src/gromacs/nbnxm/atomdata.cpp` was fixed by passing the constructor's LJ-PME state into `set_lj_parameter_data()`. This removed the build warning where a function pointer was treated as an always-true condition. It is a correctness cleanup, not a validated throughput gain.
- The current storage-reuse baseline was retested against the remaining GPU/NBNXM toggles at actual `-ntomp 16` for 4000 steps. The reference was `107.363 ns/day`. `GMX_PCFF_EXACT_RESPA_GPU_NATIVE_MULTI_NB=0` fell to `100.516 ns/day`, with `NB X/F buffer ops.` increasing to `0.320 s` and update/bond-add also rising. `GMX_PCFF_EXACT_RESPA_GPU_DIRECT_PAIR_KERNEL=1` fell to `104.591 ns/day`, mostly from higher `NB X/F` and update time. `GMX_PCFF_EXACT_RESPA_GPU_BATCH_FORCE_ONLY_COPYBACK=1` fell sharply to `88.047 ns/day`: wait time dropped, but `eR GPU add F` rose to `0.205 s`, `eR CPU listed` to `0.317 s`, and `NB X/F buffer ops.` to `0.376 s`, so the copyback batching moved work into slower host reductions.

- A scoped NBNXM force-reduction worker cap was prototyped and removed after diagnosis. Limiting only the final NBNXM force-reduction/add worker count did not isolate the hot loop safely: 8 and 4 workers collapsed to `1.952` and `1.344 ns/day`, with `Force`, `eR force setup`, `eR CPU listed`, `NB X/F`, and `Update` all exploding. The 2-worker case was terminated after startup, and 1 worker only reached `59.452 ns/day`. This indicates partial OpenMP team-size changes inside the exact r-RESPA GPU force path conflict with surrounding libgomp scheduling and should not be left as a default or diagnostic patch.
- The actual-16 OpenMP wait-policy default remains `GOMP_SPINCOUNT=7000 OMP_WAIT_POLICY=active`. A 4000-step sweep showed `15000` slightly above `7000`, but the promoted 20000-step check reversed: `7000` reached `108.471 ns/day`, while `15000` fell to `100.812 ns/day` with worse `NB X/F`, `Update`, and `eR GPU add F`. Lower spin counts (`1000`, `3000`) and very high spin (`50000`) were also worse in 4000-step screening.
- GPU update is not available for the current prod-before-start TPR. A direct `-update gpu` probe failed before integration because Nose-Hoover temperature coupling is not supported by the GPU update task, so the `Update` timer remains a CPU-side bottleneck unless the physical/control setup is changed.
- OpenMP affinity overrides are not a valid actual-16 fix for this run. `OMP_PROC_BIND=close OMP_PLACES=cores` disables GROMACS internal thread pinning, and the 4000-step actual-16 check collapsed to `6.185 ns/day`: `NB X/F buffer ops.` rose to `7.974 s`, `eR CPU listed` to `3.293 s`, `eR bond add F` to `3.166 s`, and `Update` to `4.411 s`. The cap path stayed at 8 OpenMP threads but the 4000-step result was `184.724 ns/day`, slightly below the contemporary cap-8 reference of `186.559 ns/day`; the wait-policy default should remain limited to the cap-disabled actual-16 opt-out path.

A 100-step cap check preserved `.edr/.trr/.xtc` hashes, but the promoted 20000-step check only moved `192.754 -> 192.973 ns/day` while `.trr/.xtc/.gro` diverged. Timers showed only tiny wait reductions (`Wait GPU NB local 1.713 -> 1.700 s`, `eR bond wait 0.891 -> 0.872 s`) offset by `Update 0.125 -> 0.133 s` and `eR bond add F 0.166 -> 0.171 s`. Because the speedup is noise-level and the longer trajectory is not bitwise stable, this patch is not accepted.

The LJ14 CPU path is already eligible for the analytic `do_pairs_simple<SimdReal>` route when virial/FEP/user-table conditions are absent. Moving LJ14 to GPU with `class2-pair14` removes `eR CPU listed`, but the accepted 20000-step result is slower because GPU add/wait and `NB X/F` increase.
- The exact r-RESPA GPU OpenMP cap is still best at 8 after storage reuse. A current 4000-step sweep gave cap 4/6/7/8/9/10/12 = `169.840`, `182.843`, `176.164`, `186.559`, `163.013`, `165.021`, `162.653 ns/day`. Cap 8 had the best balance; cap 6 increased `NB X/F` and `eR CPU listed`, while cap 10+ increased update/setup overhead.
- Deferring the native-multi nonbonded wait across GPU bonded work was tested two ways and removed. The scratch-merge version passed a 100-step `.edr/.trr/.xtc` check but fell from `192.858` to `190.662 ns/day` at 20000 steps; `Wait GPU NB local`, `eR bond wait`, and `Update` all increased. The direct-listed version also passed the short strict-file check, but 4000-step throughput fell `187.118 -> 178.999 ns/day` because `NB X/F buffer ops.` increased `0.055 -> 0.085 s` and `eR bond add F` increased `0.031 -> 0.056 s`. Reordering the additions did not create useful overlap and made host reductions worse.
- `GMX_PCFF_EXACT_RESPA_GPU_BONDED_CLEAR_HOST_FORCE_BUFFER=1` is not useful on the cap path. In a 4000-step check it reduced `eR bond add F` slightly but lowered total throughput `186.680 -> 183.332 ns/day`; `Force`, `Wait GPU NB local`, and `eR bond wait` increased.
- GPU bonded ftype decomposition showed why single-ftype offload numbers are misleading. Offloading only bond/angle/dihedral/improper class2 makes `eR bond wait` nearly disappear, but only because the remaining class2 work moves to CPU and hides the GPU wait. Full `class2` remains the right default; `class2-pair14` was also slower in a cap-path 4000-step check (`177.746 ns/day`) because pair14 GPU offload raised `NB X/F` and bonded add/wait costs.
- TPR-level class2 parameter accounting found a narrow zero-subterm optimization opportunity in GPU `ANGLE_CLASS2`. In the current 7907-atom pme4 TPR there are `14281` weighted angle-class2 interactions; `2500` of them (`17.5%`) have `bb_k=ba_k1=ba_k2=0` and `k3=k4=0`. The first implementation split BA1 and BA2 force math independently. It preserved the 100-step `.edr/.trr/.xtc` hashes, but slowed the 4000-step cap path to `182.255 ns/day` because `eR bond wait` rose `0.170 -> 0.177 s`, `eR bond add F` `0.036 -> 0.046 s`, and `NB X/F buffer ops.` `0.062 -> 0.076 s`; this was rejected as branch/register overhead from over-splitting the hot kernel.
- The accepted angle-class2 zero-subterm patch keeps the original grouped BA math for nonzero BA terms and only skips the grouped bond-bond / bond-angle blocks when their coefficients are zero. It preserves 100-step `.edr/.trr/.xtc` hashes and improves the cap path: 4000-step `186.559 -> 188.842 ns/day`, and 20000-step `192.754 -> 194.881 ns/day`. The 20000-step `.edr` hash matched the reference; `.trr/.xtc` differed as in other long GPU compile-variant comparisons. Timing suggests the net gain comes from lower `Force` (`3.101 -> 3.061 s`), `Wait GPU NB local` (`1.713 -> 1.667 s`), and `eR bond wait` (`0.891 -> 0.842 s`), despite slight increases in host add/buffer timers.
- The same patch does not solve actual forced-16 OpenMP. With `GMX_PCFF_EXACT_RESPA_GPU_NTOMP_MAX=0 GOMP_SPINCOUNT=7000 OMP_WAIT_POLICY=active`, the 4000-step actual-16 run was `103.806 ns/day`, while the capped 8-thread path with the patch was `188.842 ns/day`. The remaining actual-16 cliff is still CPU-side OpenMP/reduction/update overhead: actual16 vs capped on 4000 steps had `NB X/F buffer ops.` `0.306 vs 0.065 s`, `eR bond add F` `0.184 vs 0.039 s`, `eR CPU listed` `0.132 vs 0.039 s`, and `Update` `0.129 vs 0.026 s`.
- A small actual-16-only native-multi add-F path is kept. It uses a serial add only for small exact r-RESPA native multi contribution buffers when the effective NBNXM OpenMP count is at least 16; the threshold is controlled by `GMX_PCFF_EXACT_RESPA_NATIVE_MULTI_SERIAL_ADD_ATOMS` and can be disabled with `=0`. The first version applied too broadly and slowed the capped 4000-step path (`188.842 -> 183.910 ns/day`) because even threshold/env checks in the hot path were too costly. After gating to `nth >= 16` and caching the threshold, the 20000-step capped path was effectively unchanged (`194.881 -> 194.566 ns/day`), while actual-16 with `GOMP_SPINCOUNT=7000 OMP_WAIT_POLICY=active` improved slightly (`108.471 -> 109.536 ns/day`). The gain is small: `eR bond add F` improved `0.882 -> 0.832 s` and `NB X/F buffer ops.` `1.437 -> 1.411 s`, while `eR CPU listed` and `Update` moved slightly worse.
- Pair14 CPU-listed thread capping was prototyped and removed after diagnosis. A trace confirmed the remaining CPU-listed default work is level-1 `LennardJones14` (`16476` interactions), so the test limited only that pair14-only `ListedForces` object to 8 threads while leaving mdrun at actual 16. Hashes still matched over 100 steps, but performance collapsed to `1.898 ns/day`: `NB X/F buffer ops.` rose to `0.695 s`, `Update` to `0.431 s`, and `eR bond add F` to `0.281 s` in only 100 steps. This reproduces the partial OpenMP team-size switching failure mode and should not be retried as a default.
- Skipping empty CPU-listed exact levels was also removed. It reduced `eR CPU listed` call count in a 100-step cap run (`354 -> 101`) and preserved hashes, but 4000-step performance collapsed: capped `188.842 -> 126.856 ns/day` and actual16 `103.806 -> 68.282 ns/day`. Timers showed worse `eR bond wait`, `eR bond add F`, `NB X/F`, and `Update`, so the nominally empty calls appear to be part of the current GPU/CPU pacing and OpenMP scheduling balance.
- A later actual-16 rebuild/recheck changed the working baseline substantially. ## Interpretation

The mixed-precision batch performance is real and is around 1450 ns/day median, but it uses 2 fs time steps, H-bond constraints, PME order 4, and PME GPU. The PCFF exact r-RESPA example uses 0.5 fs time steps, no constraints, class2 PCFF terms, force-buffer merging, and originally PME order 5.

The time-step difference alone is a 4x ns/day difference. The pme-order-4 PCFF ceiling run at 0.5 fs gives 180.883 ns/day; a purely arithmetic 2 fs equivalent would be about 724 ns/day, but that is not a validated physical or algorithmic setting.

Current evidence supports:

- Current PCFF exact r-RESPA throughput at the tested 0.5 fs settings is roughly `344 ns/day` for the original pme-order-5 production TPR and `438-440 ns/day` for the pme-order-4 PME-GPU ceiling probe.
- 500 ns/day is not reached yet on the tested 7907-atom PCFF exact r-RESPA setup. The remaining gap is primarily GPU NB/bonded execution plus synchronization and host force-copy/add/update work; the tested stream, kernel-parameter, buffer-operation, and reduction rewrites did not close it.
- 1000 ns/day is not supported by current evidence for PCFF exact r-RESPA on this example.
