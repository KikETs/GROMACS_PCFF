# M9 Performance Notes

## Bottom Line

M9 did not implement PCFF bonded GPU kernels because the current evidence does not support the cost.

The representative benchmark puts the class2 bonded arithmetic share at about `20.1%` of total flop accounting, or about `23.6%` if listed `1-4` work is added. That implies a whole-run perfect-offload upper bound of only about `1.25x` to `1.31x`.

That is too small to justify four new bonded GPU kernels plus long-term parity maintenance, especially because the listed `1-4` GPU path is not yet correct for PCFF `9-6`.

## Measurement Source

This build does not expose an isolated CPU listed-force wallcycle subtable suitable for a stable automated M9 gate.

Instead, the test uses two log sources that are available in routine builds:

1. `REAL CYCLE AND TIME ACCOUNTING`
   - parsed by [extractWallcycleSeconds](../src/programs/mdrun/tests/pcff_short_md.cpp#L1416)
   - used to read the total `Force` wall time
2. `M E G A - F L O P S A C C O U N T I N G`
   - parsed by [extractMegaFlopsPercent](../src/programs/mdrun/tests/pcff_short_md.cpp#L1444)
   - used to estimate the relative bonded share

This means the M9 speedup numbers are **upper bounds**, not measured isolated CPU-bonded walltime speedups.

The percentage shares were stable across repeated runs and are the values that matter here. The absolute `force_s` value is machine-load-sensitive and is not the decision criterion.

## Why These Numbers Matter

They cut against the default assumption that bonded GPU offload is automatically worthwhile.

Even if class2 bonded work were removed from the CPU with zero overhead, the whole-run upside on this representative system would still be modest.

Real kernels would do worse than the upper bound because they add:

- device kernel launch overhead
- force-buffer integration complexity
- parity-maintenance cost
- future GPU-resident dataflow interactions

The broader listed `1-4` contribution is also blocked by correctness today.

## Correctness Constraint

The current GPU bonded/listed implementation is not general enough for PCFF listed `1-4` interactions:

- GPU listed-pair kernel is hardcoded `12-6`:
  [listed_forces_gpu_internal_shared.h](../src/gromacs/listed_forces/listed_forces_gpu_internal_shared.h#L751)
- CPU listed-pair path already supports general repulsion power and therefore exact PCFF `9-6`:
  [pairs.cpp](../src/gromacs/listed_forces/pairs.cpp#L656)

Because of that mismatch, M9 adds an explicit rejection for `-bonded gpu` when `reppow != 12`:

- [listed_forces_gpu_impl.cpp](../src/gromacs/listed_forces/listed_forces_gpu_impl.cpp#L145)

This is not a performance choice. It is a correctness requirement.

## Recommended Policy

Enable bonded GPU only when all of the following are true:

1. the system does not rely on sixth-power / `9-6` listed `1-4` semantics, or the GPU listed-pair path has been generalized exactly
2. representative profiling shows bonded work is a materially larger fraction than the current `20.1%` class2 subtotal
3. parity tests exist for every newly offloaded class2 bonded term

Avoid bonded GPU for PCFF/class2 now:

- the semantics are incomplete for listed `1-4`
- the projected gain is modest
- the maintenance cost is high

## What To Revisit Later

Re-open bonded GPU only if one of these changes:

1. larger production systems show a much higher bonded share
2. listed `1-4` GPU semantics are generalized from `12-6` to exact `9-6`
3. bonded CPU work becomes the dominant blocker after the nonbonded GPU path is fully resident and stable
